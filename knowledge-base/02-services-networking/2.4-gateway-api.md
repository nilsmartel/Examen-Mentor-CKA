# 2.4 — Gateway API

**Domain:** Services & Networking (20%) · **Lab:** `labs/lab-2.4-gateway-api.md`
**Prereqs:** [[2.3-ingress-controllers]]. **New in the 2025 curriculum — know it.**

## Learning objectives
The student can: explain the three core Gateway API resources and their role split, and read/write a
simple HTTPRoute.

## Teaching notes

**Gateway API is the successor to Ingress** — more expressive, role-oriented, and extensible. It is
**not built into core** (installed as CRDs via `gateway.networking.k8s.io`). It splits what Ingress
crammed into one object across **three resources with three owners**:

- **GatewayClass** — the *type* of gateway/implementation (like a StorageClass but for gateways).
  Provided by the controller vendor. *(cluster operator)*
- **Gateway** — an actual running listener: protocol, port, hostnames. References a GatewayClass.
  *(cluster/infra operator)*
- **HTTPRoute** — the routing rules (host/path/header → backend Service). Attaches to a Gateway.
  *(app developer)*

```
GatewayClass  ← (vendor/impl)
   ▲
Gateway       ← listeners (port/protocol/hostnames)
   ▲ attaches
HTTPRoute     ← rules: match path/header -> backendRefs: Service:port
```

**Minimal HTTPRoute:**
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: {name: web-route}
spec:
  parentRefs:
    - name: my-gateway                 # the Gateway it attaches to
  hostnames: ["shop.example.com"]
  rules:
    - matches:
        - path: {type: PathPrefix, value: /api}
      backendRefs:
        - {name: api-svc, port: 80}
    - matches:
        - path: {type: PathPrefix, value: /}
      backendRefs:
        - {name: web-svc, port: 80}
```
And the Gateway it points at:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: {name: my-gateway}
spec:
  gatewayClassName: <installed-class>
  listeners:
    - {name: http, protocol: HTTP, port: 80}
```

**Why it exists (vs Ingress):** standardized advanced routing (header/method/weight-based traffic
splitting) without vendor-specific annotations, and clean separation of operator vs developer concerns.

## Exam traps
- Gateway API CRDs must be **installed** first (`kubectl get gatewayclass` should work) — it's not built in.
- `parentRefs` (HTTPRoute→Gateway) and `gatewayClassName` (Gateway→GatewayClass) must line up.
- Right `apiVersion` group: `gateway.networking.k8s.io` (not `networking.k8s.io`).
- Cross-namespace attachment needs `ReferenceGrant` — mention if the task spans namespaces.

## Docs (allowed in exam)
- `kubernetes.io/docs/concepts/services-networking/gateway/`
- `gateway-api.sigs.k8s.io` is NOT in the allowed set — rely on `kubernetes.io/docs` Gateway pages.

## Socratic checks (model answers)
1. *Name the three resources and who owns each.* → GatewayClass (vendor), Gateway (infra operator),
   HTTPRoute (developer).
2. *How does an HTTPRoute attach to a Gateway?* → via `parentRefs`.
3. *Is Gateway API built into Kubernetes core?* → no; installed as CRDs.
