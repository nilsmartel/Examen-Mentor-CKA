# 2.6 — CoreDNS & Cluster DNS

**Domain:** Services & Networking (20%) · **Lab:** `labs/lab-2.6-coredns.md`
**Prereqs:** [[2.2-services-endpoints]]. Central to [[5.5-services-networking-troubleshooting]].

## Learning objectives
The student can: state the DNS names for Services and pods, verify resolution from a pod, and locate/
inspect CoreDNS.

## Teaching notes

**CoreDNS is the cluster DNS server**, running as a Deployment in `kube-system`, fronted by a Service
named **`kube-dns`** (historical name) with a stable ClusterIP. Every pod's `/etc/resolv.conf` points
at that ClusterIP (injected by the kubelet), so pods resolve cluster names automatically.

**Service DNS names (memorize the format):**
```
<service>.<namespace>.svc.cluster.local
```
- Same namespace: just `<service>` works (search-domain magic in resolv.conf).
- Cross namespace: `<service>.<namespace>` (or the FQDN).
- Headless service: returns the **pod IPs** (A records) instead of the ClusterIP.

**Pod DNS (less common but examinable):**
```
<pod-ip-with-dashes>.<namespace>.pod.cluster.local     # e.g. 10-244-0-5.default.pod.cluster.local
```

**resolv.conf inside a pod** (show it — it explains the "short name works" magic):
```
nameserver 10.96.0.10                 # the kube-dns ClusterIP
search <ns>.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```
`ndots:5` means short names get the search domains appended — that's why `web` resolves to
`web.<ns>.svc.cluster.local`.

**Verify / troubleshoot:**
```bash
kubectl get svc -n kube-system kube-dns
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl -n kube-system get configmap coredns -o yaml     # the Corefile
kubectl run t --image=busybox:1.28 -it --rm -- nslookup <svc>.<ns>.svc.cluster.local
kubectl run t --image=busybox:1.28 -it --rm -- cat /etc/resolv.conf
```
> Use `busybox:1.28` for nslookup — newer busybox has a broken nslookup in some builds.

**Common DNS failure causes:** CoreDNS pods crashlooping/scaled to 0; the `kube-dns` Service broken;
a NetworkPolicy blocking egress to port 53; wrong FQDN.

## Exam traps
- Using the wrong FQDN structure (`svc.cluster.local` for Services vs `pod.cluster.local` for pods).
- `nslookup` "fails" only because of a bad busybox image — use `busybox:1.28` or `nicolaka/netshoot`.
- DNS blocked by an egress NetworkPolicy (see [[2.5-network-policies]]).

## Socratic checks (model answers)
1. *FQDN of Service `api` in namespace `shop`?* → `api.shop.svc.cluster.local`.
2. *Why does the short name `api` resolve from a pod in `shop`?* → the `search` domains + `ndots:5` in
   the pod's resolv.conf.
3. *DNS is down cluster-wide — first two things to check?* → CoreDNS pods in kube-system and the
   `kube-dns` Service.
