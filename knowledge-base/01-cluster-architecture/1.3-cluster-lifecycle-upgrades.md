# 1.3 — Cluster Lifecycle & Upgrades

**Domain:** Cluster Architecture (25%) · **Lab:** `labs/lab-1.3-drain-upgrade.md`
**Prereqs:** [[1.2-kubeadm-install-prereqs]], [[5.1-cluster-node-troubleshooting]].

## Learning objectives
The student can: drain/cordon a node safely, and recite/execute the kubeadm upgrade order for
control-plane and worker nodes.

## Teaching notes

**Upgrade one minor version at a time** (e.g. 1.34 → 1.35, never skip). Order matters:
**control plane first, then workers.** Within a node the order is: upgrade the `kubeadm` binary →
`kubeadm upgrade` → upgrade `kubelet`+`kubectl` binaries → restart kubelet.

**Control-plane node upgrade:**
```bash
# 1) upgrade kubeadm binary (package manager), then:
sudo kubeadm upgrade plan                       # shows target versions
sudo kubeadm upgrade apply v1.35.x              # upgrades the control-plane static pods
# 2) drain, upgrade kubelet/kubectl, restart:
kubectl drain <cp-node> --ignore-daemonsets
sudo apt-get install -y kubelet=1.35.x kubectl=1.35.x   # (or dnf)
sudo systemctl daemon-reload && sudo systemctl restart kubelet
kubectl uncordon <cp-node>
```

**Worker node upgrade** (run `kubectl` from a machine that still has cluster access):
```bash
kubectl drain <worker> --ignore-daemonsets --delete-emptydir-data
# on the worker: upgrade kubeadm binary, then:
sudo kubeadm upgrade node                       # NOTE: 'upgrade node', not 'apply'
# upgrade kubelet+kubectl binaries, then:
sudo systemctl daemon-reload && sudo systemctl restart kubelet
kubectl uncordon <worker>
```
Key difference: control plane uses `kubeadm upgrade apply <version>`; **workers use `kubeadm upgrade node`**.

**drain / cordon / uncordon:**
- `cordon` — mark unschedulable; existing pods stay.
- `drain` — cordon **and evict** pods so you can do maintenance. Needs `--ignore-daemonsets` (DS pods
  can't be evicted normally) and `--delete-emptydir-data` if pods use emptyDir. `--force` for bare pods
  not backed by a controller.
- `uncordon` — return to scheduling.

**Version skew:** kubelet may be **up to 3 minor versions older** than the API server, never newer.
kubeadm supports upgrading one minor at a time. Don't let a worker's kubelet be newer than the API server.

## Exam traps
- Using `kubeadm upgrade apply` on a **worker** (wrong — that's `kubeadm upgrade node`).
- Forgetting `systemctl daemon-reload && systemctl restart kubelet` after installing the new kubelet.
- Draining without `--ignore-daemonsets` → command errors out.
- Skipping a minor version.

## Socratic checks (model answers)
1. *Upgrade order — control plane or workers first?* → control plane first, one minor version at a time.
2. *Which kubeadm command on a worker vs control plane?* → worker: `kubeadm upgrade node`;
   control plane: `kubeadm upgrade apply vX.Y.Z`.
3. *`drain` errors because of DaemonSet pods — what flag?* → `--ignore-daemonsets`.
