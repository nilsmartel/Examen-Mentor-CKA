# 1.1 — RBAC (Role-Based Access Control)

**Domain:** Cluster Architecture (25%) · **Lab:** `labs/lab-1.1-rbac.md`
**Prereqs:** basic kubectl. Foundational; teach early.

## Learning objectives
The student can: create Roles/ClusterRoles and bind them to users/groups/ServiceAccounts, and verify
permissions with `kubectl auth can-i`.

## Teaching notes

**Four objects, two axes.** RBAC = a **verb** allowed on a **resource**, granted to a **subject**.
- **Role** = permissions **within one namespace**. **ClusterRole** = permissions **cluster-wide**
  (or for cluster-scoped resources like nodes, PVs, namespaces themselves).
- **RoleBinding** = grants a Role (or a ClusterRole) **to subjects in one namespace**.
- **ClusterRoleBinding** = grants a ClusterRole **cluster-wide**.

Mental model (the axis trick):
| Binding \ Role | Role | ClusterRole |
|---|---|---|
| **RoleBinding** | perms in that namespace | ClusterRole's perms, **limited to that namespace** |
| **ClusterRoleBinding** | ❌ invalid | perms in **all** namespaces |

The bottom-left combo (RoleBinding → ClusterRole) is a common, useful pattern: define a reusable
ClusterRole once, grant it namespace-by-namespace.

**Subjects:** `User`, `Group` (both are just strings K8s trusts the authenticator to assert — there is
no User object), and `ServiceAccount` (a real in-cluster object for pods).

**Rules:** each rule = `apiGroups` + `resources` + `verbs` (+ optional `resourceNames`).
- Core API group is `""` (empty string): pods, services, configmaps, secrets, PVs/PVCs, nodes.
- Named groups: `apps` (deployments, daemonsets), `rbac.authorization.k8s.io`, `networking.k8s.io`, etc.
- Verbs: `get list watch create update patch delete deletecollection`. `*` = all.

**ServiceAccounts:** every pod runs as an SA (`default` if unspecified). To give a pod API powers,
create an SA, bind a Role to it, and set `spec.serviceAccountName` on the pod. Tokens are
auto-projected into the pod at `/var/run/secrets/kubernetes.io/serviceaccount/`.

**Imperative creation (exam speed):**
```bash
kubectl create role reader --verb=get,list,watch --resource=pods -n web
kubectl create rolebinding reader-bind --role=reader --user=jane -n web
kubectl create clusterrole node-reader --verb=get,list --resource=nodes
kubectl create clusterrolebinding node-reader-bind --clusterrole=node-reader --user=jane
kubectl create sa build -n web
kubectl create rolebinding build-bind --role=reader --serviceaccount=web:build -n web
```

**Verify — the single most important RBAC command:**
```bash
kubectl auth can-i list pods -n web --as=jane
kubectl auth can-i create deployments -n web --as=system:serviceaccount:web:build
kubectl auth can-i '*' '*' --as=jane           # is jane admin?
kubectl auth can-i --list --as=jane -n web
```

## Exam traps
- **Wrong apiGroup:** deployments are in `apps`, not `""`. Using the wrong group silently grants nothing.
- Binding a **Role** with a **ClusterRoleBinding** is invalid; and RoleBinding→Role is namespace-local.
- SA subject syntax in bindings: `--serviceaccount=<namespace>:<name>` (imperative) →
  becomes `kind: ServiceAccount, name, namespace` in YAML.
- Forgetting `-n` puts the Role/RoleBinding in `default`, not the target namespace.

## Socratic checks (model answers)
1. *You want jane to read pods in `web` only. Which two objects?* → a Role (in web) + a RoleBinding
   (in web) to user jane.
2. *How do you grant the same ClusterRole in three namespaces?* → three **RoleBindings** (one per ns)
   referencing the ClusterRole — not a ClusterRoleBinding.
3. *How do you prove it worked?* → `kubectl auth can-i get pods -n web --as=jane`.
