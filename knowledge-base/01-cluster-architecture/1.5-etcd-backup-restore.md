# 1.5 — etcd Backup & Restore

**Domain:** Cluster Architecture (25%) · **Lab:** `labs/lab-1.5-etcd-backup-restore.md`
**Prereqs:** [[5.2-control-plane-components]] (static pods). **Fully practicable via `minikube ssh`.**

## Learning objectives
The student can: take an etcd snapshot with `etcdctl`, and restore it, adjusting the etcd static-pod
data directory. This is a **classic guaranteed exam task** — drill it to fluency.

## Teaching notes

**etcd is the cluster's database** — all API objects live there. Backup = a **snapshot** of etcd;
restore = load that snapshot into a fresh data dir and point etcd at it.

**Everything needs certs + endpoint.** etcd requires mTLS. On a kubeadm node the cert paths are in the
etcd static-pod manifest (`/etc/kubernetes/manifests/etcd.yaml`) — read them there if unsure:
- `--endpoints=https://127.0.0.1:2379`
- `--cacert=/etc/kubernetes/pki/etcd/ca.crt`
- `--cert=/etc/kubernetes/pki/etcd/server.crt`
- `--key=/etc/kubernetes/pki/etcd/server.key`
Set `ETCDCTL_API=3` (default on modern etcd, but set it to be safe).

**Backup (snapshot save):**
```bash
sudo ETCDCTL_API=3 etcdctl snapshot save /var/lib/etcd-backup/snap.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
# verify:
sudo ETCDCTL_API=3 etcdctl snapshot status /var/lib/etcd-backup/snap.db --write-out=table
```

**Restore (snapshot restore) — the steps that trip people up:**
```bash
# 1) restore INTO A NEW data dir (never overwrite the live one directly):
sudo ETCDCTL_API=3 etcdctl snapshot restore /var/lib/etcd-backup/snap.db \
  --data-dir=/var/lib/etcd-restored
# 2) point the etcd static pod at the new dir by editing the manifest:
#    in /etc/kubernetes/manifests/etcd.yaml, change the hostPath volume for etcd-data
#    from /var/lib/etcd  ->  /var/lib/etcd-restored
# 3) the kubelet restarts etcd automatically. Verify the cluster's data is back.
```
Because moving the etcd manifest / editing it restarts etcd (and briefly the API server), expect a
short control-plane blip during restore — that's normal.

**Key insight:** the restore's `--data-dir` and the etcd manifest's volume path **must agree**. Most
failures are a path mismatch or forgetting to update the manifest.

## Exam traps
- Missing/incorrect `--cacert/--cert/--key` → "context deadline exceeded" or auth errors. Read the real
  paths from `etcd.yaml`.
- Restoring over the live `/var/lib/etcd` while etcd is running — restore to a **new** dir and repoint.
- Forgetting to edit the static-pod manifest so etcd actually uses the restored data.
- Wrong endpoint port (2379 client, 2380 peer).

## Socratic checks (model answers)
1. *What three cert flags does every etcdctl command need, and where do you find their paths?* →
   `--cacert/--cert/--key`; read them from `/etc/kubernetes/manifests/etcd.yaml`.
2. *After `snapshot restore --data-dir=/var/lib/etcd-restored`, what must you change?* → the etcd
   static-pod manifest's hostPath volume to point at the restored dir.
3. *Why restore to a new dir instead of the existing one?* → to avoid corrupting/locking the live data
   dir while etcd is running; then repoint cleanly.
