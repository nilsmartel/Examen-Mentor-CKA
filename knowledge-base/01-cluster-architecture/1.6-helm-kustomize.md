# 1.6 — Helm & Kustomize

**Domain:** Cluster Architecture (25%) · **Lab:** `labs/lab-1.6-helm-kustomize.md`
**Prereqs:** basic manifests. New emphasis in the 2025 curriculum.

## Learning objectives
The student can: install/upgrade/rollback a Helm chart and set values; and build/apply a Kustomize
overlay with `kubectl -k`.

## Teaching notes

### Helm — the package manager
A **chart** is a packaged app (templates + default `values.yaml`). A **release** is an installed
instance. Helm renders templates with values and applies the result.
```bash
helm repo add <name> <url>                       # e.g. add a public chart repo
helm repo update
helm search repo <term>
helm create demo                                 # scaffold a LOCAL chart (great for offline practice)
helm install myrel ./demo --set service.type=ClusterIP   # install a release (chart dir or <repo>/<chart>)
helm install myrel ./demo -f my-values.yaml              # or a values file
helm list                                                 # releases
helm upgrade myrel ./demo --set replicaCount=3           # change it
helm rollback myrel 1                                     # revert to revision 1
helm uninstall myrel
helm template myrel ./demo                                # render WITHOUT installing (inspect)
helm show values ./demo                                   # what can I set?
```
`helm template` and `helm show values` are the exam-useful "what would this do / what can I tune" tools.
Note: exam docs tab allows `helm.sh/docs`. (The public Bitnami chart repo was retired in 2025 — use
`helm create` for reliable local practice; treat repo commands as syntax you should know.)

### Kustomize — template-free overlays (built into kubectl)
Kustomize customizes plain YAML with a `kustomization.yaml` — **no templating language**. A **base**
holds common manifests; **overlays** patch them per environment.
```
base/
  kustomization.yaml     # resources: [deployment.yaml, service.yaml]
  deployment.yaml
overlays/prod/
  kustomization.yaml     # resources: [../../base]; patches, replicas, images, namePrefix, labels
```
`kustomization.yaml` common fields: `resources`, `namespace`, `namePrefix`/`nameSuffix`,
`labels` (the modern replacement for the deprecated `commonLabels`), `images` (override tags),
`replicas`, `patches` (strategic-merge or JSON6902), `configMapGenerator`/`secretGenerator`.
(Note: `bases:` is deprecated — list bases under `resources:` instead.)
```bash
kubectl kustomize overlays/prod        # render to stdout (inspect)
kubectl apply -k overlays/prod         # build + apply in one step
kubectl delete -k overlays/prod
```

**Helm vs Kustomize (one line):** Helm = templated, versioned, packaged releases with rollback;
Kustomize = declarative patch layering over raw YAML, no templating, native to kubectl.

## Exam traps
- `kubectl apply -k <dir>` vs `kubectl apply -f` — use `-k` for a kustomization directory.
- Forgetting `helm repo update` → stale/"chart not found".
- Editing rendered output instead of `values.yaml`/overlay — changes get lost on upgrade.
- `configMapGenerator` adds a content hash suffix to the name (triggers rollout on change) — expected.

## Socratic checks (model answers)
1. *Inspect what a chart will create without installing it?* → `helm template` (or `helm install --dry-run`).
2. *Revert a bad Helm upgrade?* → `helm rollback <release> <revision>`.
3. *Apply a Kustomize overlay?* → `kubectl apply -k <overlay-dir>`.
