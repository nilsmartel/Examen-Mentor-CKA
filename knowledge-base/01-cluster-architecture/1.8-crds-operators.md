# 1.8 — CRDs & Operators

**Domain:** Cluster Architecture (25%) · **Lab:** `labs/lab-1.8-crd-operator.md`
**Prereqs:** basic manifests, [[1.1-rbac]] (operators need RBAC).

## Learning objectives
The student can: recognize/inspect a CRD, create instances of a custom resource, and explain what an
operator does and how to install one.

## Teaching notes

**CRD = Custom Resource Definition.** It extends the Kubernetes API with a *new kind* of object. Once a
CRD is installed, you `kubectl get/apply` your custom resource just like a built-in.
```bash
kubectl get crds                                  # what custom kinds exist
kubectl get crd <name> -o yaml                    # its schema, group, versions, scope
kubectl api-resources | grep <group>              # your new kind + short names + apiVersion
kubectl explain <yourkind>                         # works once the CRD is installed
```
A CRD defines: `group`, `versions` (with an OpenAPI schema), `scope` (Namespaced/Cluster), and
`names` (kind, plural, singular, shortNames). After it's applied, you create **custom resources (CRs)**:
```yaml
apiVersion: stable.example.com/v1
kind: Widget
metadata: {name: w1}
spec: {size: 3}
```
`kubectl apply -f widget.yaml` — the API server stores it. **A CRD alone does nothing** but store data.

**Operator = CRD + controller.** The controller (a pod running in the cluster) *watches* the custom
resources and drives real-world state to match their `spec` (the reconcile loop). That's the operator
pattern: encode operational knowledge ("how to run Postgres/Prometheus") as software.
```bash
# typical operator install is just applying manifests or a Helm chart:
kubectl apply -f https://.../operator.yaml     # installs CRDs + controller Deployment + RBAC
helm install my-op <repo>/<operator-chart>
kubectl get pods -n <operator-ns>              # the controller
kubectl get crds                                # the CRDs it added
```
Operators bundle: the **CRDs**, a **controller Deployment**, and the **RBAC** (SA + ClusterRole/Binding)
the controller needs to watch/modify resources.

## Exam traps
- Expecting a CRD to *do* something — it only defines a type; you need the controller/operator for behavior.
- `kubectl explain <kind>` failing because the CRD isn't installed yet (order: CRD first, then CRs).
- Forgetting the operator's RBAC — the controller pod can't reconcile without permissions.
- Right `apiVersion` (group/version) on the custom resource must match the CRD's served version.

## Socratic checks (model answers)
1. *What does a CRD by itself accomplish?* → it adds a new API type; it stores objects but takes no
   action without a controller.
2. *What turns a CRD into an operator?* → a controller that watches the custom resources and reconciles
   real state to their spec.
3. *How do you list all custom resource types in a cluster?* → `kubectl get crds` /
   `kubectl api-resources`.
