# 5.3 — Monitoring Resource Usage

**Domain:** Troubleshooting (30%) · **Lab:** `labs/lab-5.3-resource-monitoring.md`
**Prereqs:** [[5.4-container-output-logs]]. Enables [[3.3-autoscaling-hpa]].

## Learning objectives
The student can: enable metrics-server, use `kubectl top`, and identify the pod/node consuming the
most CPU/memory.

## Teaching notes

**`kubectl top` needs the metrics-server.** It is *not* installed by default. The metrics-server
scrapes the kubelet's `/metrics/resource` endpoint and serves the **metrics.k8s.io** API (Resource
Metrics API). Without it, `kubectl top` errors with "Metrics API not available", and HPA can't scale
on CPU/memory.

On minikube: `minikube addons enable metrics-server`. On a real cluster you'd apply the
metrics-server manifest (and often add `--kubelet-insecure-tls` in labs due to self-signed kubelet certs).

**Commands:**
```bash
kubectl top nodes                       # CPU/memory per node (and % of allocatable)
kubectl top pods -A                     # per pod
kubectl top pods -n web --sort-by=cpu   # find the hog
kubectl top pod mypod --containers      # per-container breakdown
```
Give it ~1 minute after enabling before numbers appear (it needs a scrape window).

**Reading the numbers:** `kubectl top nodes` shows usage vs the node's **allocatable** capacity. High
memory near the limit → risk of `MemoryPressure` and OOM eviction. Correlate a hot pod with
`kubectl describe node` (which shows requests/limits committed) — the exam likes "which pod is using
the most X" tasks.

**requests vs limits vs actual usage** (important distinction, connects to [[3.5-scheduling-affinity-taints-limits]]):
- **requests** = what the scheduler reserves (used for placement).
- **limits** = the ceiling the runtime enforces (CPU throttled, memory OOM-killed).
- **`kubectl top`** = *actual* live usage — which may be well below requests or bumping limits.

**metrics-server ≠ monitoring stack.** It's for `top`/HPA only (short-term, in-memory). Long-term
metrics/dashboards would be Prometheus — out of scope for CKA.

## Exam traps
- Running `kubectl top` before metrics-server is ready → "error: Metrics API not available". Enable
  it and **wait**.
- Confusing `describe node` "Requests/Limits" (reservations) with `top` (actual usage).

## Socratic checks (model answers)
1. *`kubectl top pods` errors. Why and fix?* → metrics-server not installed/ready;
   `minikube addons enable metrics-server`, wait ~1 min.
2. *Difference between a pod's memory **request** and what `kubectl top` shows?* → request =
   scheduler reservation; `top` = actual current usage.
3. *How do you find the highest-CPU pod cluster-wide?* → `kubectl top pods -A --sort-by=cpu`.
