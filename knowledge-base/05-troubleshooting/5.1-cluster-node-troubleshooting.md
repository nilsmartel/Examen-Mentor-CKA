# 5.1 — Cluster & Node Troubleshooting

**Domain:** Troubleshooting (30%) · **Lab:** `labs/lab-5.1-node-troubleshooting.md`
**Prereqs:** basic kubectl. Pairs with [[5.2-control-plane-components]].

## Learning objectives
The student can: diagnose a `NotReady` node, inspect the kubelet, read node conditions, and restore
a node to `Ready`.

## Teaching notes

**The debugging staircase — teach this order, it applies to almost every troubleshooting task:**
1. `kubectl get nodes` / `kubectl get pods -A` — what's actually broken?
2. `kubectl describe node/pod <x>` — look at **Conditions** and **Events** at the bottom.
3. `kubectl logs` (for pods) — app-level failure.
4. `ssh` to the node → `systemctl status kubelet`, `journalctl -u kubelet` — node/kubelet level.

**Node status = the kubelet's heartbeat.** Each node runs a **kubelet** that posts status to the API
server. If the kubelet stops or can't reach the API server, the node goes **`NotReady`** after the
node-monitor grace period (~40s). Pods on a NotReady node are eventually evicted/marked for deletion.

**Node conditions** (`kubectl describe node`): `Ready`, `MemoryPressure`, `DiskPressure`,
`PIDPressure`, `NetworkUnavailable`. `Ready=True` is the goal. Pressure conditions cause the
scheduler to avoid the node and can trigger eviction.

**Where node problems actually come from (exam-realistic):**
- **kubelet not running** → `sudo systemctl status kubelet`; start/enable it. Root cause often a bad
  `--config` (`/var/lib/kubelet/config.yaml`) or a bad `/etc/kubernetes/kubelet.conf` (kubeconfig
  the kubelet uses to talk to the API server).
- **kubelet running but node NotReady** → CNI not installed/broken (`NetworkUnavailable`), or the
  kubelet can't reach the API server (wrong server URL / expired cert in `kubelet.conf`).
- **Disk/Memory pressure** → free space or evict; check `df -h`, `crictl` image cleanup.
- **swap on** → modern kubelet may refuse to start if swap misconfigured; classic gotcha
  (`swapoff -a`, though newer versions have swap support).

**Key commands on the node:**
```bash
systemctl status kubelet          # is it up?
systemctl restart kubelet         # after a config fix
journalctl -u kubelet -f          # WHY it won't start — read the actual error
crictl ps ; crictl ps -a          # container-runtime view (kubeadm nodes)
crictl logs <container-id>
```

**cordon / drain / uncordon** (also lives in [[1.3-cluster-lifecycle-upgrades]] but troubleshooting-relevant):
```bash
kubectl cordon <node>                 # mark unschedulable (no new pods)
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data  # evict pods for maintenance
kubectl uncordon <node>               # back into rotation
```

## Exam traps
- People edit YAML and forget the fix is on the **node** (kubelet/systemd), not in the API.
- After fixing kubelet config you must `systemctl restart kubelet` (or `daemon-reload` if you touched
  a systemd unit) — the change isn't live otherwise.
- `describe` **Events** are truncated by age; also check `kubectl get events -A --sort-by=.lastTimestamp`.

## Socratic checks (model answers for the mentor)
1. *A node shows `NotReady`. What are your first three commands?*
   → `kubectl describe node X` (conditions/events), then on the node `systemctl status kubelet` and
   `journalctl -u kubelet`.
2. *kubelet won't start after a config edit — where do you look?* → `journalctl -u kubelet` for the
   parse/validation error; the config is `/var/lib/kubelet/config.yaml`; restart after fixing.
3. *What's the difference between `cordon` and `drain`?* → cordon only stops *new* scheduling; drain
   also *evicts* existing pods.
