# 5.2 — Control-Plane Component Troubleshooting

**Domain:** Troubleshooting (30%) · **Lab:** `labs/lab-5.2-control-plane.md`
**Prereqs:** [[5.1-cluster-node-troubleshooting]], [[1.5-etcd-backup-restore]] (etcd context).

## Learning objectives
The student can: locate and repair a broken **static pod** control-plane component (API server,
controller-manager, scheduler, etcd) on a kubeadm node.

## Teaching notes

**In a kubeadm cluster the control plane runs as STATIC PODS.** The kubelet watches a directory —
`/etc/kubernetes/manifests/` — and runs whatever manifests are there, *directly*, without the API
server's involvement. That's why the control plane can boot before the API server exists.

Files there: `kube-apiserver.yaml`, `kube-controller-manager.yaml`, `kube-scheduler.yaml`, `etcd.yaml`.

**How to fix a static pod:** edit the manifest file **on the node** → the kubelet notices and
recreates the pod automatically (no `kubectl apply`). Static-pod pods appear in `kube-system` with the
node name suffixed (e.g. `kube-apiserver-minikube`) but you **cannot** edit them via `kubectl edit` —
the source of truth is the file.

**Diagnosis path when the control plane is sick:**
```bash
kubectl get pods -n kube-system                 # if API server is UP
# If the API SERVER itself is down, kubectl won't work at all. Go to the node:
sudo crictl ps -a | grep -E "apiserver|etcd|scheduler|controller"
sudo crictl logs <container-id>                 # the real error
sudo cat /var/log/pods/... ; ls /etc/kubernetes/manifests/
journalctl -u kubelet | grep -i "apiserver\|manifest"
```

**The classic exam scenario:** a typo was introduced into `kube-apiserver.yaml` (bad flag, wrong
image tag, wrong port, bad `--etcd-servers`, a misindented YAML). Symptoms: `kubectl` hangs / "connection
refused". Fix on the node by correcting the manifest; the kubelet restarts the pod. Watch with
`crictl ps` until the apiserver container is running, then `kubectl get nodes` works again.

**Common breakages & where they show:**
- **API server down** → `kubectl` = connection refused. Check manifest + `crictl logs` of the
  apiserver container. Common causes: bad flag, wrong `--etcd-servers`/certs, port clash.
- **Scheduler down** → new pods stay **`Pending`** forever (nothing assigns a node). `kubectl get
  pods -n kube-system` shows scheduler crashlooping.
- **Controller-manager down** → things that should self-heal don't: deployments don't create
  replicasets, endpoints don't populate, tokens aren't issued.
- **etcd down** → API server can't start / data operations fail. See [[1.5-etcd-backup-restore]].

**Certificates:** control-plane comms use certs under `/etc/kubernetes/pki/`. Expired certs
(`kubeadm certs check-expiration`) break the API server; `kubeadm certs renew all` fixes them.

## Exam traps
- Trying to `kubectl edit` a static pod — it won't stick. **Edit the file on the node.**
- Moving/renaming a manifest out of `/etc/kubernetes/manifests/` **stops** that component (sometimes
  the intended fix during etcd restore). Moving it back restarts it.
- YAML indentation in the manifest — a single bad space crashes the component.

## Socratic checks (model answers)
1. *`kubectl` gives "connection refused". Where do you go?* → to the node; the API server static pod
   is down. Inspect `/etc/kubernetes/manifests/kube-apiserver.yaml` and `crictl logs` of its container.
2. *You edited a static-pod manifest — how do you apply it?* → you don't; save the file and the
   kubelet recreates the pod. Watch with `crictl ps`.
3. *New pods are stuck `Pending` and nodes are healthy — which component?* → the **scheduler**.
