# 5.5 — Services & Networking Troubleshooting

**Domain:** Troubleshooting (30%) · **Lab:** `labs/lab-5.5-network-troubleshooting.md`
**Prereqs:** [[2.2-services-endpoints]], [[2.6-coredns]], [[2.5-network-policies]].

## Learning objectives
The student can: debug why a Service returns no traffic, distinguish selector/port/endpoint/DNS/
NetworkPolicy causes, and verify each hop of the request path.

## Teaching notes

**Trace the request path hop by hop — this is the whole skill:**
```
client → Service (ClusterIP) → EndpointSlice (the pod IPs) → kube-proxy rules → Pod → container port
                    ▲ also: DNS resolves the Service name        ▲ also: NetworkPolicy may block
```

**The #1 Service bug: selector ≠ pod labels → no endpoints.** A Service selects pods by label. If the
selector doesn't match any pod labels, the Service has **zero endpoints** and silently drops traffic.
```bash
kubectl get endpoints <svc>              # EMPTY = broken. This is the fastest diagnosis.
kubectl get endpointslices -l kubernetes.io/service-name=<svc>
kubectl get svc <svc> -o wide            # see the selector
kubectl get pods --show-labels           # compare to pod labels
```
If endpoints are empty → fix the selector or the pod labels so they match.

**The other Service bug: wrong `targetPort`.** Service `port` is what clients hit; `targetPort` must
equal the **container's** listening port. Mismatch → connection refused even with good endpoints.

**Systematic checklist (teach as a routine):**
1. `kubectl get endpoints <svc>` — populated? If empty → selector/label mismatch or pods not Ready.
2. Are the backing pods **Ready**? Not-ready pods are excluded from endpoints (failing readiness probe).
3. `targetPort` == container port? `containerPort` is just documentation; the real port is what the app binds.
4. **DNS**: from a test pod, `nslookup <svc>` / `nslookup <svc>.<ns>.svc.cluster.local`. Broken →
   see [[2.6-coredns]] (CoreDNS pods, the `kube-dns` Service).
5. **NetworkPolicy**: a default-deny policy in the namespace can block traffic even when everything
   else is right — `kubectl get netpol -n <ns>`. See [[2.5-network-policies]].
6. **kube-proxy**: on the node, is kube-proxy running? (rarely the exam answer, but complete the path.)

**Test tooling:**
```bash
kubectl run tmp --image=nicolaka/netshoot -it --rm -- bash   # curl, nslookup, dig, nc, tcpdump
# or lightweight:
kubectl run tmp --image=busybox -it --rm -- sh   # wget, nslookup
# from inside:
curl http://<svc>.<ns>:<port>
nslookup <svc>.<ns>.svc.cluster.local
nc -zv <svc> <port>
```

**NodePort/LoadBalancer extras:** NodePort must be in range **30000–32767**; test with
`curl <nodeIP>:<nodePort>`. On minikube, `minikube service <svc> --url` gives a reachable URL.

## Exam traps
- Debugging the pod when the **Service selector** is the bug — always check `get endpoints` first.
- Readiness probe failing → pod excluded from endpoints → "service down" though the pod is `Running`.
- Forgetting a namespace-wide default-deny NetworkPolicy is silently blocking traffic.
- `containerPort` in the manifest is cosmetic; the app's actual bind port is what matters for `targetPort`.

## Socratic checks (model answers)
1. *A Service returns nothing. What's the single fastest command to start with?* →
   `kubectl get endpoints <svc>` — empty means selector/label/readiness problem.
2. *Endpoints are populated but curl is refused — next suspect?* → `targetPort` vs the container's
   actual listening port.
3. *Everything looks right but traffic is still blocked in one namespace — what did you forget?* →
   a default-deny **NetworkPolicy**.
