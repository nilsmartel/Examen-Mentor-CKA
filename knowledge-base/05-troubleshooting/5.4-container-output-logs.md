# 5.4 — Container Output Streams & Logging

**Domain:** Troubleshooting (30%) · **Lab:** `labs/lab-5.4-logging.md`
**Prereqs:** basic pods. Foundational for all troubleshooting — teach early.

## Learning objectives
The student can: read pod/container logs (incl. previous crashed container), interpret pod states and
container exit codes, and use events to explain a failing pod.

## Teaching notes

**The four states a broken pod shows — teach the meaning of each, they map to different fixes:**
- **`Pending`** — not scheduled yet. Causes: no node fits (resources/affinity/taints), unbound PVC,
  scheduler down. → `kubectl describe pod` Events; check requests, taints, PVC.
- **`ImagePullBackOff` / `ErrImagePull`** — can't pull the image. Causes: typo in image name/tag,
  private registry without imagePullSecret, no network. → `describe` Events show the pull error.
- **`CrashLoopBackOff`** — container starts then exits repeatedly. The app itself is failing. →
  **logs**, especially `--previous`.
- **`Running` but not working** — app-level bug, bad config, failing probe. → logs + `exec`.

**Logs:**
```bash
kubectl logs <pod>                       # single-container pod
kubectl logs <pod> -c <container>        # multi-container / init containers
kubectl logs <pod> --previous            # logs of the LAST crashed instance (crashloop gold)
kubectl logs <pod> -f --tail=50          # follow
kubectl logs -l app=web --all-containers # by label across pods
```
Kubernetes captures **stdout/stderr** of PID 1 in the container — that's what `kubectl logs` shows.
Apps that log to a file inside the container won't appear in `kubectl logs` (design point / trap).

**Exit codes (visible in `describe` → Last State):**
- `0` clean exit · `1` general app error · `137` = 128+9 = **SIGKILL** (often **OOMKilled** — memory
  limit hit) · `143` = 128+15 = SIGTERM · `139` = segfault.
- `describe pod` shows `Last State: Terminated, Reason: OOMKilled, Exit Code: 137` — that's your
  smoking gun for a too-low memory limit.

**Events are half the battle:**
```bash
kubectl describe pod <pod>                     # Events at the bottom
kubectl get events -n <ns> --sort-by=.lastTimestamp
kubectl get events --field-selector involvedObject.name=<pod>
```

**Init & ephemeral debug:**
```bash
kubectl logs <pod> -c <init-container>         # init container logs
kubectl debug -it <pod> --image=busybox --target=<container>   # ephemeral debug container
```

## Exam traps
- Forgetting `--previous` on a CrashLoopBackOff — the *current* container may have no logs yet.
- App logs to a file, not stdout → `kubectl logs` is empty; check the app's design / `exec` in.
- Misreading `ImagePullBackOff` (registry/name problem) as a crash (app problem).

## Socratic checks (model answers)
1. *Pod is `CrashLoopBackOff`. Which single flag most likely reveals the cause?* → `kubectl logs
   <pod> --previous`.
2. *Exit code 137 — what happened?* → SIGKILL, almost always **OOMKilled**; raise the memory limit
   or fix the leak.
3. *`ImagePullBackOff` vs `CrashLoopBackOff` — which is an app bug?* → CrashLoop (app runs then
   fails); ImagePull is a registry/name/secret problem, app never started.
