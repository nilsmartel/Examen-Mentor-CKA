# 3.4 — Self-Healing Primitives

**Domain:** Workloads & Scheduling (15%) · **Lab:** `labs/lab-3.4-self-healing.md`
**Prereqs:** [[3.1-deployments-rollouts]].

## Learning objectives
The student can: choose the right controller (Deployment/ReplicaSet/DaemonSet/StatefulSet/Job),
configure probes, and explain how each supports self-healing.

## Teaching notes

**Controllers = self-healing.** Each reconciles actual → desired continuously, replacing failed pods.
Pick by intent:
- **Deployment/ReplicaSet** — N identical, interchangeable, stateless pods. (RS is what Deployments manage.)
- **DaemonSet** — exactly one pod **per node** (matching nodeSelector/tolerations). Log/monitoring/CNI
  agents. Auto-adds a pod when a node joins.
- **StatefulSet** — stable identity: ordered names (`web-0`, `web-1`), stable per-pod DNS (via a
  **headless Service**), and stable per-pod storage (`volumeClaimTemplates`). Ordered, graceful
  rollout. For databases/clustered apps.
- **Job / CronJob** — run-to-completion (Job) and scheduled (CronJob) workloads. `completions`,
  `parallelism`, `backoffLimit`; CronJob `schedule` (cron), `concurrencyPolicy`.

**Probes (the self-healing dials — know all three):**
- **livenessProbe** — is it alive? Fail → kubelet **restarts** the container. Fixes hangs/deadlocks.
- **readinessProbe** — is it ready for traffic? Fail → pod **removed from Service endpoints** (not
  restarted). This is the one behind many "service down but pod Running" cases (see [[5.5-services-networking-troubleshooting]]).
- **startupProbe** — for slow starters; disables liveness/readiness until it passes once, so slow boot
  isn't killed by liveness.

Probe handlers: `httpGet`, `tcpSocket`, `exec`. Tunables: `initialDelaySeconds`, `periodSeconds`,
`failureThreshold`, `timeoutSeconds`.
```yaml
readinessProbe:
  httpGet: {path: /healthz, port: 8080}
  initialDelaySeconds: 5
  periodSeconds: 10
```

**restartPolicy:** `Always` (default, Deployments), `OnFailure`/`Never` (Jobs). Pod-level.

## Exam traps
- Confusing liveness (restarts) vs readiness (removes from endpoints) — different failure behavior.
- StatefulSet without its **headless Service** → no stable DNS.
- DaemonSet pods can't be evicted by a plain `drain` — need `--ignore-daemonsets`.
- Liveness with too-short `initialDelaySeconds` → restart loop on a slow-starting app (use startupProbe).

## Socratic checks (model answers)
1. *A readiness probe fails — what happens to the pod?* → removed from Service endpoints; **not** restarted.
2. *You need one pod per node for a log agent — which controller?* → DaemonSet.
3. *Why does a StatefulSet need a headless Service?* → for stable per-pod DNS identity.
