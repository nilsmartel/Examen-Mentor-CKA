# 3.1 — Deployments, Rolling Updates & Rollbacks

**Domain:** Workloads & Scheduling (15%) · **Lab:** `labs/lab-3.1-rollouts.md`
**Prereqs:** basic pods (student already knows deployments — use a diagnostic, credit if solid).

## Learning objectives
The student can: perform a rolling update, control its strategy, roll back to a prior revision, and
read rollout history.

## Teaching notes
> The learner already knows deployments/replicasets conceptually. Focus on the **operational** verbs
> and edge cases the exam tests, not the basics.

**Deployment → ReplicaSet → Pods.** A Deployment manages ReplicaSets; each rollout creates a **new**
ReplicaSet and scales it up while scaling the old one down. Old ReplicaSets are kept (up to
`revisionHistoryLimit`, default 10) so you can roll back.

**Rollout controls:**
```bash
kubectl set image deploy/web web=nginx:1.27       # triggers a rolling update
kubectl rollout status deploy/web                  # watch it progress
kubectl rollout history deploy/web                 # revisions
kubectl rollout history deploy/web --revision=2    # details of one revision
kubectl rollout undo deploy/web                    # roll back to previous
kubectl rollout undo deploy/web --to-revision=1    # to a specific revision
kubectl rollout pause deploy/web ; kubectl rollout resume deploy/web
kubectl rollout restart deploy/web                 # re-roll pods (e.g. to pick up a changed secret)
```

**RollingUpdate strategy (the two knobs):**
```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%   # how many pods can be down during the update
      maxSurge: 25%         # how many EXTRA pods can be created above desired
```
`Recreate` strategy kills all old pods before creating new — causes downtime; used when versions can't
coexist.

**Change cause / annotations:** `kubectl annotate deploy/web kubernetes.io/change-cause="v1.27"` makes
`rollout history` meaningful. (Older `--record` is deprecated.)

**Scaling & autoscaling hook:** `kubectl scale deploy/web --replicas=5`; HPA (see
[[3.3-autoscaling-hpa]]) manages replicas automatically.

## Exam traps
- Editing a pod directly instead of the Deployment — the controller reverts it.
- Expecting `rollout undo` to restore data — it only restores the pod template/spec.
- A stuck rollout (`rollout status` hangs) is usually the new pods failing (ImagePull/CrashLoop) —
  debug the new ReplicaSet's pods; consider `rollout undo`.

## Socratic checks (model answers)
1. *Update the image and watch progress — two commands?* → `kubectl set image ...` then
   `kubectl rollout status deploy/web`.
2. *Roll back to revision 1?* → `kubectl rollout undo deploy/web --to-revision=1`.
3. *`maxSurge` vs `maxUnavailable`?* → surge = extra pods above desired during update; unavailable =
   how many may be missing.
