# 3.5 — Scheduling: Requests/Limits, Affinity, Taints & Tolerations

**Domain:** Workloads & Scheduling (15%) · **Lab:** `labs/lab-3.5-scheduling.md`
**Prereqs:** [[3.1-deployments-rollouts]], [[5.4-container-output-logs]] (Pending diagnosis).

## Learning objectives
The student can: control pod placement with requests, nodeSelector/affinity, and taints/tolerations,
and diagnose why a pod is Pending.

## Teaching notes

**Resource requests & limits (placement + enforcement):**
- **requests** — reserved for scheduling; the scheduler only places a pod on a node with enough
  unrequested capacity. Too-high requests → **Pending** (Insufficient cpu/memory).
- **limits** — runtime ceiling: CPU is **throttled** at the limit; memory over the limit → **OOMKilled**
  (exit 137, see [[5.4-container-output-logs]]).
- **QoS classes:** `Guaranteed` (limits==requests for all resources), `Burstable` (some requests),
  `BestEffort` (none). Affects eviction order under pressure.

**Node selection — three tools, increasing power:**
1. **nodeSelector** — simple equality match on node labels. `spec.nodeSelector: {disktype: ssd}`.
2. **nodeAffinity** — expressive: `requiredDuringScheduling...` (hard) vs
   `preferredDuringScheduling...` (soft, weighted). Operators: `In`, `NotIn`, `Exists`, etc.
3. **podAffinity / podAntiAffinity** — schedule near/away from *other pods* (by label), using
   `topologyKey` (e.g. hostname, zone). Anti-affinity spreads replicas across nodes.

**Taints & tolerations (the repel/permit pair) — teach the polarity carefully:**
- A **taint on a node** repels pods: `kubectl taint nodes n1 key=val:NoSchedule`.
- A **toleration on a pod** lets it be scheduled onto a tainted node anyway.
- Effects: `NoSchedule` (don't place), `PreferNoSchedule` (avoid if possible), `NoExecute` (also
  **evict** existing non-tolerating pods).
- Remove a taint: `kubectl taint nodes n1 key=val:NoSchedule-` (trailing `-`).
- **Key mental model:** taints/tolerations only *repel/permit* — they don't *attract*. To force a pod
  onto specific nodes you also need nodeSelector/affinity. Control-plane nodes are tainted by default
  (that's why normal pods avoid them).

**nodeName** — bypasses the scheduler entirely; pins a pod to a node by name (also how you'd schedule
when the scheduler is down — connects to [[5.2-control-plane-components]]).

**Diagnosing Pending:** `kubectl describe pod` → Events. Common: Insufficient cpu/memory, no node
matches nodeSelector/affinity, untolerated taint, unbound PVC.

## Exam traps
- Taint without a matching toleration → pod stuck **Pending**. Add the toleration OR remove the taint.
- Toleration ≠ attraction — pod may still land elsewhere unless also constrained by affinity.
- `requiredDuringScheduling` (hard) vs `preferred` (soft) — hard can cause Pending; soft won't.
- CPU limit throttles (no kill); memory limit **kills** (OOM).

## Socratic checks (model answers)
1. *A pod is Pending after you tainted its only node — fix options?* → add a matching toleration to the
   pod, or remove the taint (`...:NoSchedule-`).
2. *Does a toleration guarantee a pod lands on the tainted node?* → no; it only permits — you need
   affinity/nodeSelector to attract.
3. *Memory limit exceeded vs CPU limit exceeded — what happens?* → memory ⇒ OOMKilled; CPU ⇒ throttled.
