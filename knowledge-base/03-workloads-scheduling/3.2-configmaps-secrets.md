# 3.2 — ConfigMaps & Secrets

**Domain:** Workloads & Scheduling (15%) · **Lab:** `labs/lab-3.2-config-secrets.md`
**Prereqs:** basic pods.

## Learning objectives
The student can: create ConfigMaps/Secrets imperatively and consume them as env vars or mounted files,
and knows how Secret encoding/security actually works.

## Teaching notes

**ConfigMap = non-secret config; Secret = sensitive data.** Both are key/value stores you inject into
pods. **Two consumption modes** — this is the core exam skill:

**As environment variables:**
```yaml
envFrom:
  - configMapRef: {name: app-config}     # all keys as env vars
env:
  - name: DB_HOST                         # one specific key
    valueFrom:
      configMapKeyRef: {name: app-config, key: db_host}
  - name: DB_PASS
    valueFrom:
      secretKeyRef: {name: db-secret, key: password}
```

**As mounted files (a volume):**
```yaml
volumes:
  - name: cfg
    configMap: {name: app-config}         # each key becomes a file
containers:
  - volumeMounts:
      - {name: cfg, mountPath: /etc/config, readOnly: true}
```
Key difference: **env vars are captured at pod start** (changing the ConfigMap does NOT update running
env vars — needs a pod restart). **Mounted ConfigMaps/Secrets update in place** (eventually) without a
restart, though apps must re-read the file.

**Imperative creation (exam speed):**
```bash
kubectl create configmap app-config --from-literal=db_host=db --from-literal=mode=prod
kubectl create configmap app-config --from-file=./config.props        # file(s) as keys
kubectl create secret generic db-secret --from-literal=password=s3cret
kubectl create secret tls web-tls --cert=tls.crt --key=tls.key        # TLS secret
kubectl create secret docker-registry regcred --docker-server=... --docker-username=... --docker-password=...
```

**Secret reality check (say this clearly):** Secret values are **base64-encoded, NOT encrypted** at
rest by default — base64 is trivially reversible (`echo <val> | base64 -d`). Real protection needs
encryption-at-rest config + RBAC. Don't let the student think base64 = security.

## Exam traps
- Changing a ConfigMap and expecting **env-var** consumers to see it — they won't until restart
  (`kubectl rollout restart`). Mounted files do update.
- `--from-literal` (inline) vs `--from-file` (file contents) vs `--from-env-file` (KEY=VAL lines).
- Secret `data:` is base64; `stringData:` lets you write plaintext in the manifest.

## Socratic checks (model answers)
1. *You updated a ConfigMap; env-var consumers didn't change. Why/fix?* → env vars are read at start;
   `kubectl rollout restart` the workload (or use a mounted volume).
2. *Is a Secret encrypted by default?* → no — base64-encoded; needs encryption-at-rest + RBAC for real security.
3. *Inject one Secret key as env var — which field?* → `valueFrom.secretKeyRef`.
