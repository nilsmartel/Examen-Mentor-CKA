# 4.2 — PersistentVolumes & PersistentVolumeClaims

**Domain:** Storage (10%) · **Lab:** `labs/lab-4.2-pv-pvc.md`
**Prereqs:** [[4.1-volumes-access-modes-reclaim]].

## Learning objectives
The student can: create a PV + PVC, get them bound, mount the PVC in a pod, and diagnose a Pending PVC.

## Teaching notes

**The PV/PVC split = separation of concerns.** The **PV** is the actual storage (created by an admin or
dynamically). The **PVC** is a *request* for storage by a user/pod ("I need 1Gi RWO"). Kubernetes
**binds** a PVC to a suitable PV; the pod references the **PVC**, never the PV directly.

**Binding rules (why a PVC stays Pending):** a PVC binds to a PV only if the PV satisfies **all** of:
- capacity ≥ request,
- access modes ⊇ requested modes,
- storageClassName matches,
- selector/volume constraints (if any).
No matching PV → PVC is **Pending** (unless a StorageClass dynamically provisions one — see
[[4.3-storage-classes-dynamic-provisioning]]).

**Static example:**
```yaml
apiVersion: v1
kind: PersistentVolume
metadata: {name: pv1}
spec:
  capacity: {storage: 1Gi}
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath: {path: /mnt/data}       # lab-only backend
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: pvc1}
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: manual
  resources: {requests: {storage: 500Mi}}
```
Mount it in a pod:
```yaml
volumes:
  - name: data
    persistentVolumeClaim: {claimName: pvc1}
containers:
  - volumeMounts: [{name: data, mountPath: /data}]
```

**Lifecycle/status:** PV phases `Available → Bound → Released → Failed`. PVC `Pending → Bound`.
```bash
kubectl get pv,pvc
kubectl describe pvc pvc1        # Events explain why it's not binding
```

**Key subtlety:** `storageClassName: ""` explicitly means "no class / static binding only" and differs
from omitting it (which uses the default class). Mismatched class names are a top cause of Pending PVCs.

## Exam traps
- **Pending PVC:** capacity too big, access mode not offered by any PV, or `storageClassName` mismatch.
- Data persists across pod restarts because it's on the PV — deleting the **pod** doesn't delete the data;
  deleting the **PVC** may (per reclaim policy).
- A PV in `Released` (Retain policy) won't auto-rebind to a new PVC.

## Socratic checks (model answers)
1. *A PVC is Pending — name three things that must match a PV.* → capacity, access modes, storageClassName.
2. *Does the pod reference the PV or the PVC?* → the PVC (`persistentVolumeClaim.claimName`).
3. *Delete the pod — is the data gone?* → no; it's on the PV. Deleting the PVC is what may reclaim it.
